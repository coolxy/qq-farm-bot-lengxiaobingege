## 产品简介

### 它是什么

一个部署在您自己服务器上的农场自动化助手，由两部分组成：

- **core 后端**：以子进程 Worker 隔离运行每个游戏账号，通过微信小游戏协议与服务器通信，执行挂机策略
- **web 面板**：Vue 3 单页应用，由后端托管，提供账号管理、策略配置、实时状态与日志查看

### 能做什么

| 能力 | 说明 |
| --- | --- |
| 多账号挂机 | 每个账号独立进程运行，互不干扰；掉线自动重登；支持抓包 Code 与微信扫码两种登录方式 |
| 农场自动化 | 收获、种植、浇水、除草、除虫、施肥、土地升级全流程自动化，策略可按账号配置 |
| 好友自动化 | 偷菜、帮忙、捣乱合并为单次访问，支持黑名单、安静时段与互动上限 |
| 活动自动化 | 奶茶热销中、快乐不独享、节令日历等活动的全流程自动化，单步容错，详见[活动自动化](#活动自动化) |
| 经营分析 | 作物收益分析、策略预览、背包估值、商城与神秘商人价格查询 |
| 事件推送 | 基于 pushoo 的实例级通知；断线先等 150 秒自动重登，重登失败才提醒，恢复在线不打扰 |

### 适用场景与边界

适用于拥有 QQ 农场微信端账号、希望减少重复操作的个人用户。本项目不提供多用户体系，不适合作为多人共用服务对外运营。

> [!WARNING]
> 本项目仅供学习与研究用途。使用本工具可能违反游戏服务条款，由此产生的一切后果由使用者自行承担。

## 快速开始

### 环境要求

| 运行方式 | 要求 |
| --- | --- |
| 源码运行 | Node.js 20.19 或以上、pnpm 10 或以上 |

推荐通过 Corepack 启用项目指定版本的 pnpm：

```bash
corepack enable
pnpm --version
```

### 步骤一：获取并构建

```bash
git clone https://github.com/lengxiaobingege/qq-farm-bot.git
cd qq-farm-bot
pnpm install
pnpm dev
```

`pnpm dev` 会先构建前端，再启动后端。Windows、Linux、macOS 均可使用。

### 步骤二：登录管理面板

1. 服务首次启动只创建管理员账号 `admin`，密码为空。
2. 浏览器打开 `http://localhost:5173`（开发模式）或 `http://localhost:3007`（后端托管模式），登录页自动切换为「首次使用 · 设置管理员密码」。
3. 自行输入密码并确认；也可以单击「生成随机密码」按钮生成 16 位强密码并自动填入，生成后请立即保存或复制。
4. 提交后自动登录进入面板。

密码要求：至少 8 位，且包含大写字母、小写字母、数字、特殊符号中的至少 3 类。

### 步骤三：添加游戏账号

1. 进入设置页，添加游戏账号（微信扫码或抓包 Code 登录）。
2. 启用账号，系统为其启动独立 Worker。
3. 在自动化配置中勾选农场、好友、活动等策略。

### 步骤四：验证运行

1. 面板概览页应显示账号在线状态与角色 ID。
2. 实时日志应出现任务调度记录（如收获、种植、活动任务）。
3. 如配置了事件推送，手动停用账号网络后约 2 分钟内应能收到掉线通知（系统先等 150 秒自动重登，重登成功则不推送）。

### 后台常驻运行（Linux）

```bash
bash ./start.sh              # 缺依赖或代码变化时自动安装并增量重建（同时拉起看门狗）
bash ./start.sh --rebuild    # 忽略缓存完整重建
tail -f app_dev.log          # 查看日志
bash ./stop.sh               # 停止服务（先停看门狗，再停主进程与 3000 转发）

bash ./watchdog.sh status    # 查看看门狗状态与最近记录
bash ./watchdog.sh start     # 单独启动看门狗（幂等）
bash ./watchdog.sh stop      # 单独停止看门狗
tail -f watchdog.log         # 看门狗的检查与重启记录

bash ./preflight.sh          # 交付前自检：单实例、双口、转发一致性、看门狗心跳、日志、崩溃转储、账号在线
bash ./preflight.sh --full   # 额外跑一遍 core 测试套件
```

看门狗每 60 秒检查一次，只在确认主进程真的不在时才动手：

| 场景 | 行为 |
| --- | --- |
| 主进程正常、3007 可用 | 不做任何事；顺带检查 3000 转发，断了就重建 |
| 主进程不在、3007 空闲 | 调 `start.sh` 拉起，最多连续 3 次 |
| 主进程不在、3007 被本项目遗留进程占用 | 只补写 pid 文件，不重启（避免双实例重复购买） |
| 3007 被其它程序占用 | 一律不抢占，记录 `foreign(...)` 后跳过 |
| 连续 3 次拉起或健康检查失败 | 停止自动拉起，并推送一条「自动重启失败」告警 |
| 进程活着但 3007 连续 3 次无响应 | 先 TERM 再 KILL，然后重新拉起 |

`start.sh` 每次启动会把上一轮日志改名成 `app_dev.log.prev`（只留一份），因此自动重启后仍能回看崩溃或断线现场。`start.sh` 自身带目录锁，看门狗与手动启动同时触发时只有一个能继续，避免双实例重复购买。`stop.sh` 除 pid 文件外，还会按「cwd + argv」精确清理没有登记的手工实例。

> [!NOTE]
> 看门狗是普通后台进程，和主服务同生命周期。容器/沙箱整体休眠时它也会一起停，醒来后需要手动 `bash ./start.sh`；它只能救“进程自己挂了”，救不了“整机没了”。

> [!TIP]
> 仍然建议用 `start.sh` 后台启动：主进程现在会忽略 `SIGHUP`，关终端不再把进程带崩、也不再落近百 MB 的 core dump，但前台跑依旧有三处短板——日志只进终端不落文件、没有看门狗、终端被会话恢复重放时还会多起一个抢端口的实例。
>
> 也不要在终端里留 `PORT=3000 node core/client.js` 这类历史命令：开发环境的终端会话恢复会重放它。现在主进程启动时会先探测 `PORT` 是否已被监听，发现已有实例就直接退出并写日志（`端口 N 已被占用，疑似已有实例在运行`），所以只要旧实例和 socat 还活着，野实例就起不来；`preflight.sh` 还会用「pid 文件不一致 / 3007 无响应 / 看门狗未运行」三项把它抓出来，`stop.sh` 会按 cwd + argv 清理。

### 常见问题

| 问题 | 处理方式 |
| --- | --- |
| 扫码登录后不久掉线 | 系统会自动通过 refreshToken 或 openid + accessToken 重获会话；若持续掉线，重新扫码即可 |
| 管理员密码遗忘 | 属服务器运维操作，需要文件系统访问权限，流程不在公开文档中说明，请妥善保管密码 |
| 端口被占用 | 后端端口 `3007` 可在运行配置中调整；前端开发服务器端口由 Vite 自动处理 |
| 活动自动化没有执行 | 确认设置页「活动任务」自动化开关已启用；活动结束后对应条目会自动静默 |
| 想看某次协议交互细节 | 参考[项目文档](#项目文档)中对应专题文档与 tools 目录下的抓包分析脚本 |

## 功能说明

### 活动自动化

活动自动化代码位于 `core/src/services/activity-auto/`，每个活动一个独立文件，由调度器串行编排，避免并发请求触发网关限速。设计要点：

- **单步容错**：任一步骤失败（例如货币不足）只跳过该步骤，不中断整轮
- **错误去重**：同一活动的同一错误 30 分钟内不重复写日志，避免活动结束时刷屏
- **过期静默**：活动结束后对应自动化自动停止，不产生无效请求

| 活动 | 自动化流水线 |
| --- | --- |
| 奶茶热销中 | 领取收银台收益与工资 → 按店铺等级工位上限补雇员工（24 小时 → 12 小时 → 4 小时阶梯降档，有多少花多少）→ 加速收银台 → 升级店铺 → 制作饮品 → 涨薪互动 → 成长基金解锁与领取 |
| 快乐不独享 | 每日快乐值、每日首次分享、可领档位奖励 |
| 节令日历 | 节令开放当天自动执行一次（按北京时间记账）：领取奖励、本地题库答题（带题目变化防呆）、季度累计奖励 |

### 农场自动化

- 自动收获、种植、浇水、除草、除虫、铲除与土地升级

### 图鉴与藏品

- 超变图鉴依据 `Illustrated.json` 的 `param`/`type` 字段区分黄金果实、活动果实与装扮果实，不依赖名称推断

### 背包与交易

- 背包物品使用、出售与批量出售，按活动区间与过期时间智能判断可售状态
- 神秘商人活动商品、游戏商城价格折扣限购与购买

- 活动列表协议统一展示当前与已结束活动；快照请求串行合并，避免占满游戏网关请求队列

- 概览、个人、活动、好友、分析、神秘商人、游戏商城、设置页面
- Socket.IO 实时状态与日志流，液态玻璃风格界面；PC 固定侧栏，移动端顶部栏与底部导航
- 设置页统一管理游戏账号、自动化策略、运行环境、管理员密码与事件通知

### 事件推送与掉线判定

- **断线不立刻喊**：连接断开后先挂起 150 秒，把这段时间让给自动重登；期间恢复在线则完全静默
- **真失败才推**：重登三次全失败、无可用会话、持续离线超时属于终态，立即推送，不再等窗口
- **兜底不漏**：既不成功也不失败（卡住）时，150 秒到期补一条
- **恢复才闭环**：真推过「已离线」的账号，恢复后再补一条「农场已恢复在线」；没推过的不补
- **登录不打扰**：扫码登录、服务重启、自动重登成功本身都不推送，登录提醒已从 worker 移除
- **不刷屏**：同账号同类掉线 10 分钟内只推一条；推送串行发送，失败重试一次
- **会话保活**：每小时整点刷新一次会话，成功不推送，失败才提醒
- **重启不误报**：`stop.sh` 先停 worker 再退主进程，worker 主动停止不进提醒流程，运维重启不会换来一条「已离线」

判定流程与参数说明见[事件推送与掉线判定](docs/event-notify.md)。

## 🔐 管理端安全设计

面板不设注册体系，全局仅一名超级管理员，账号固定为 `admin`。本章说明安全机制的设计原理与使用边界。

### 凭据模型

| 阶段 | 触发条件 | 行为 |
| --- | --- | --- |
| 未初始化 | `admin.json` 不存在或标记 `needsSetup` | 登录接口拒绝一切密码尝试，登录页自动切换为「设置管理员密码」表单 |
| 已初始化 | 首次设置完成 | 进入常规登录；设置接口永久失效，无法被再次调用覆盖凭据 |

设计取舍：

- **无预设密码、无默认密码、无后门**。从根上消除"部署后未及时改密"这一最常见的事故窗口，攻击者不存在可以猜的默认值。
- **明文密码永不落盘、不经网络回传**。首次设置时密码仅存在于浏览器到服务器的单次请求中，服务端只保存 PBKDF2 派生哈希（SHA-512、10 万次迭代、32 字节随机盐），此后没有任何命令或接口能读回密码。
- **登录页内置 16 位随机密码生成器**。基于浏览器 `crypto.getRandomValues` 密码学安全随机源，四类字符齐全，剔除易混淆字符 `0O1lI`，生成值自动填入并支持一键复制。
- **密码策略**：至少 8 位，且包含大写字母、小写字母、数字、特殊符号中的至少 3 类，拒绝常见弱口令字典。

### 防爆破与锁定

- 双层限流：每个 IP 每分钟最多 10 次请求；登录失败 5 次锁定该 IP 15 分钟，窗口自动过期清理
- 锁定按 IP 分桶而非全局锁账号：单一来源的暴力尝试不会把账号整体锁死形成拒绝服务，也无法通过更换用户名绕过
- 客户端 IP **默认只认 TCP 对端**：未配置 `TRUSTED_PROXY_IPS` 时，`X-Forwarded-For` / `X-Real-IP` / `CF-Connecting-IP` 一律忽略，伪造请求头无法换取新的限流桶
- 部署在 Nginx/Caddy/CLB 之后时，必须把**代理自身的真实 IP** 填入 `TRUSTED_PROXY_IPS`（逗号分隔，不要填网段）；Express 的 `trust proxy` 与本白名单联动，不填则按直连处理
- 登录成功与失败（含来源 IP）全部落日志，可审计

### 哈希与找回

- 密码只以 PBKDF2（SHA-512、10 万次迭代、32 字节盐）格式存储，校验使用 `crypto.timingSafeEqual` 常量时间比较
- 早期无盐 `SHA-256` 摘要格式已**停止兼容**：这类哈希一旦泄露可被直接离线爆破，检测到只会拒绝登录，需要重设密码，不再"透明升级"
- 管理员密码丢失后的找回属于服务器运维操作，需要文件系统级访问权限，具体流程不在本公开文档中说明

### 凭据轮换

一旦怀疑 `admin.json`、`admin-sessions.json` 或 `core/data/` 曾被提交、备份外泄或截图泄露，按以下顺序处理：

1. 用新密码重算 `admin.json` 的 `password` 字段（`salt:hash` 格式，PBKDF2-SHA512/10 万次/64 字节）
2. 将 `admin-sessions.json` 重置为 `{"tokens":[],"savedAt":"..."}`，让所有已签发令牌立即失效
3. 清空 `login-attempts.json`，避免旧锁定记录干扰
4. 重启服务使内存中的凭据缓存失效（`admin-store` 会缓存已加载的管理员记录）
5. 若旧哈希曾进入版本库，用 `git filter-repo` 从历史中抹除并强推，同时视为该密码已永久泄露

### 部署侧加固清单

程序边界之外的安全，需要您在基础设施层完成：

- [ ] 不要将 `3007`/`5173` 直接暴露公网；生产环境使用 Nginx/Caddy 反向代理 + HTTPS，面板路径叠加访问控制（IP 白名单或 Basic Auth）
- [ ] `core/data/` 目录包含账号凭据、会话令牌与运行数据：权限建议 700，纳入备份但绝不提交到公开仓库
- [ ] 定期审计 `core/data/logs/` 中 `admin` 模块日志，关注异常来源 IP
- [ ] 公网部署建议配置实例级事件推送（pushoo），终态掉线与异常第一时间知晓
- [ ] 反向代理之后部署时设置 `TRUSTED_PROXY_IPS`，否则所有请求都会被识别为代理 IP，限流退化为全局单桶
- [ ] `.env` 权限设为 `600`；它虽然只含端口与时区，但同目录可能追加其他本地配置

### 依赖基线

传递依赖通过 `pnpm-workspace.yaml` 的 `overrides` 钉到已修版本（`proxy-addr`、`body-parser`、`qs`、`engine.io`、`socket.io-parser`、`ws`、`form-data`、`lodash`、`postcss`、`picomatch` 等），`pnpm audit --prod` 仅剩 5 项，且无 critical。

其中 **`protobufjs` 固定在 `8.0.2`（精确版本，不加 `^`）**，这是有意为之：

- `8.0.1` / `8.0.2` 修掉了远程代码执行与代码生成 gadget 两类严重问题，是本项目协议解析路径的必需基线
- `8.4` 起改变了 `toObject` 的默认值填充行为，`slot_index: 0`、`false`、`''` 这类显式零值字段会被丢弃。项目的协议层要求**逐字节复现官方抓包**（`tests/network-keepalive`、`farm-interaction-cleanup` 等 8 条断言直接用十六进制比对），升到 8.4+ 会直接破坏请求体一致性
- 未修的剩余项（`Any` 无限展开 DoS、递归 JSON DoS、`.proto` 死循环）都发生在**解析不可信输入**时；本项目的 protobuf 输入来自游戏服务端与仓库内的 `.proto` 文件，不在攻击者可控范围内

## 二创变更摘要

- 移除外部 farm-code 换码 fallback：微信换码仅保留本地 loginBuffer 方式
- 微信登录 buffer 失效自动重获：无 refreshToken 时自动用 openid + accessToken 重获 loginBuffer 再换码
- 移除 QQ 端：仅保留微信扫码与抓包 Code 登录
- 活动自动化重构：`activity-auto/` 按活动拆分独立文件，单步容错与错误 30 分钟去重；奶茶活动支持阶梯雇佣与按工位上限补满
- 管理员凭据加固：首次部署不预设密码，由用户在首次登录页自行设置，支持一键生成 16 位随机强密码；服务端仅存 PBKDF2 哈希，不存任何明文
- 掉线提醒改为延迟判定：断线先挂起 150 秒等自动重登，终态才立即推送，恢复在线不打扰；同账号同类 10 分钟内去重
- 通知收敛：移除 worker 侧「登录成功」推送，恢复通知只在真推过掉线后补发，避免重启即推送
- 微信会话改为整点保活：每小时刷新一次，成功静默、失败才推送；无可用会话时补发终态提醒
- 巡田补肥失败后冷却 10 分钟：化肥耗尽时不再每轮重发必然失败的施肥请求
- 日志时间统一为北京时间（UTC+8）
